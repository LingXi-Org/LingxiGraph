## Problem details

Non-2xx responses use `application/problem+json`:

```json
{
  "type": "about:blank",
  "title": "Quota Exceeded",
  "status": 429,
  "detail": "tenant queued-run quota exceeded",
  "code": "quota_exceeded",
  "request_id": "01J...",
  "retryable": true
}
```

| Field | Purpose |
| --- | --- |
| `status` | HTTP category |
| `code` | Stable machine code and preferred branch field |
| `request_id` | Correlates server logs and traces |
| `retryable` | Whether this operation can be retried with backoff |
| `detail` | Human diagnostic prose; do not parse |

Common stable codes include `idempotency_conflict`, `quota_exceeded`, and `join_timeout`, plus problem codes mapped from schema, authentication, concurrency, and resource-state failures. Treat new codes as an unknown error rather than failing to parse them.

### Steering-specific error codes

| `code` | HTTP | Triggered when |
| --- | --- | --- |
| `run_terminal` | 409 | `/steer` is called against a run in a terminal status (`succeeded`/`failed`/`cancelled`/`timed_out`/`dead_letter`); no durable write is created |
| `run_superseded` | 409 | `/steer` or `/cancel` is called against an old `run_id` already superseded by a `resume`; call it against the new run's `id` instead (see `metadata.resumed_from_run_id`). For `/cancel`, this fires even though the old run's `status` is still `paused` -- the check reads the typed `superseded_by_run_id` column, not `status` and not user-writable `metadata`, so the historical run is never mutated to `cancelled` while its resumed descendant keeps running, and the check cannot be forged via a client-submitted `metadata` key (see the operations doc's "The `superseded_by_run_id` lineage marker") |
| `payload_too_large` | 413 | Serialized `payload` + `metadata` exceed the size cap (32KB, or the server's event size cap, whichever is smaller); no durable write is created |
| `run_resume_conflict` | 409 | Concurrent resume calls raced against the same paused run; exactly one wins and creates the new run, every other caller gets this instead |
| `run_finalizing` | 409 | `/steer` is called after the run's graph has already finished executing but before its final status is committed (a short window while the worker durably flushes and finalizes); there is no safe point left to consume the event, so it is rejected rather than durably accepted with nobody to ever read it. A `paused` outcome is not affected -- steering a paused run remains normal |

## Run business errors

Successful creation returns `202 pending`. A later node/schema/provider error moves the resource to `failed`, `timed_out`, or `dead_letter` and populates:

```json
{
  "status": "failed",
  "error": {
    "code": "invalid_update",
    "message": "...",
    "retryable": false
  }
}
```

The get/join HTTP request itself may still return 200. Clients must inspect both HTTP status and `run.status`.

## SSE format and resume

```text
GET /v1/runs/{run_id}/stream
Accept: text/event-stream
Last-Event-ID: 17
```

```text
id: 18
event: node_completed
data: {"id":"...","run_id":"...","sequence":18,"kind":"node_completed","data":{},"created_at":"..."}
```

- Events are persisted in PostgreSQL before delivery.
- `sequence` increases from 1 within a run.
- Reconnect with the last processed `Last-Event-ID`; the server starts at the next event.
- Deduplicate on `(run_id, sequence)` to handle repeated delivery.
- Lines beginning `: heartbeat` are keep-alive comments and should be ignored.
- The server closes the stream when the run becomes terminal or `paused`.

### Steering lifecycle events

Besides ordinary execution events (`node_completed`, etc.), mid-run input (steering)
produces three dedicated SSE event kinds across its lifecycle:

| `kind` | Emitted when | Key fields |
| --- | --- | --- |
| `run.steer.accepted` | A `/steer` call is durably accepted (202) | `steering_event_id`, `source_event_id` (if from a resume migration), `sequence`, `kind` |
| `run.steer.consumed` | Graph code calls `drain_steering()` and that consumption is durably committed by `commit_steering_consumptions_if_owned()` | `steering_event_id`, `source_event_id`, `sequence`, `kind`, `queue_latency_seconds`, `node`, `namespace`, `task_id` |
| `run.steer.superseded` | A steering event's row durably transitions to the `superseded` disposition without ever being consumed — either because a paused run it belonged to was resumed (its still-pending steering is migrated onto the new run) or because it was still `pending`/`delivered` when the run reached its terminal-finalization boundary (see below) | `steering_event_id`, `source_event_id`, `sequence`, `kind`, `reason` (`resume_transfer` or `unconsumed_at_final_boundary`), `superseded_by_run_id` (set for `resume_transfer`, `null` for `unconsumed_at_final_boundary`), `replacement_steering_event_id` (set for `resume_transfer`, `null` for `unconsumed_at_final_boundary`) |

`run.steer.superseded`'s `unconsumed_at_final_boundary` reason is a deliberately honest,
generic label — it does **not** claim the event was racing anything. It covers every steering
row still `pending`/`delivered` once the owning worker reaches a genuinely terminal
finalization boundary, and that has more than one possible cause: a `/steer` call can durably
commit its row a moment before the worker closes new admission (a real race), but just as
commonly the graph simply never called `drain_steering()` at all for a row that had been
sitting there, fully visible, for the run's entire lifetime — ordinary application-level
non-consumption, not a race. The Runtime cannot currently distinguish these two cases from the
data it has, so it does not pretend to; both get the same `unconsumed_at_final_boundary`
reason. Rather than forcing the run through an indefinite retry loop just because a steering
event happened to exist — which would penalize a graph that legitimately never calls
`drain_steering()` at all — the Runtime durably transitions the row to `superseded` and
finalizes the run with its already-computed outcome. A `run.steer.superseded` event is never
silently dropped in this case; it is always paired with the disposition change, committed
together with the run's terminal status in the same durable transaction, and is idempotent
under retry (a repeated attempt to supersede an already-superseded row emits no duplicate
event).

Field meanings:

- `steering_event_id`: the id of the steering event under the **current** run (if the event
  was migrated from an older run, this is the fresh id it got after migration, not the id
  the client originally received);
- `source_event_id`: the **root** id the client originally received from its `/steer` call.
  Even across repeated pause/resume migrations of the same underlying steering, this field
  stays consistent at every hop, letting a client correlate the eventual
  `run.steer.consumed`/`run.steer.superseded` back to its original request. This is
  per-lifecycle-event, not a blanket rule: on `run.steer.accepted` and `run.steer.consumed` it
  is present only for events that arrived via a migration — a directly-submitted event (never
  transferred) has no `source_event_id` on those two. `run.steer.superseded` is different: it
  always sets `source_event_id` to `event.source_event_id or event.id`, so a directly-submitted
  event's superseded record still carries a root id — its own — even though it was never
  migrated;
- `sequence`: this event's position in its run's steering sequence (a separate counter from
  the run's overall event-stream `sequence`);
- `kind`: passed through from the `/steer` request body's `kind`;
- `queue_latency_seconds`: seconds from the steering event's **original** durably-accepted
  time (including time accumulated across every resume) to when it was consumed;
- `node`: the name of the node that consumed the event;
- `namespace`: the subgraph namespace path (array) the consuming node belongs to;
- `task_id`: distinguishes the specific task among parallel/`Send` tasks in the same
  superstep.

**PostgreSQL is the durable source of truth; Redis is only an optional accelerator.** All three
of `run.steer.accepted`, `run.steer.consumed`, and `run.steer.superseded` are durably written
to PostgreSQL before becoming visible anywhere else. Redis pub/sub is used only to hint
workers that "steering may be waiting," reducing polling latency. Even if that Redis
notification is lost (a dropped connection, a Redis restart), a worker still checks/polls
PostgreSQL at its next safe point and eventually consumes the event — a lost Redis
notification never permanently drops steering. Similarly, the production Worker path,
`commit_steering_consumptions_if_owned()`, is idempotent: when a worker retries the same
consumption batch after a transient failure, only events that actually transition status
produce a new `run.steer.consumed` — already-consumed events are never re-emitted. The same
holds for superseding a stale row: retrying an already-superseded transition emits no
duplicate `run.steer.superseded`.

## Retry policy

1. Use bounded exponential backoff only for `retryable=true`, network failure, 429, and transient 5xx.
2. Honor `Retry-After`.
3. Reuse the same `Idempotency-Key` and identical body when retrying run creation.
4. Resume SSE from the last sequence; do not create a new run.
5. Do not automatically redrive deterministic schema or tool-permission errors.

<Callout type="warn">
The same request key with a different body returns `409 idempotency_conflict`. Do not silently switch to a random key after conflict; that hides a caller bug and may duplicate business work.
</Callout>
